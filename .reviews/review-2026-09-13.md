## 1. Architecture Review

### 1.1 Overall shape

The architecture is a well-structured event-driven pipeline inside ESO's single-threaded Lua sandbox:

```
ESO event → EventPipeline (filter + safe-wrap)
          → EventDispatcher (type-driven routing)
          → boss.events[bucket][abilityId] (handler entry)
          → BossBase / CA / AlertSink (output)
```

The layering is clean and responsibilities are well partitioned. `EventPipeline` owns registration and teardown; `EventDispatcher` owns routing logic; boss classes own mechanic knowledge. `AlertSink` and `Bridge` decouple boss code from UI controls. No boss file touches a control, which is exactly right.

### 1.2 Event filtering (A5) — the central architectural decision

The decision to register one `EVENT_COMBAT_EVENT` handler **per ability id** rather than one unfiltered handler is the most consequential design choice in the codebase. In a 12-player trial, the unfiltered stream is thousands of events per second. The filtered approach means ESO's C++ layer rejects almost everything before Lua ever sees it. This is the correct call and it is executed correctly.

The cost is that an ability id absent from `boss.events` (or from a common module's declared set) is **never registered and therefore never dispatched** — its handler is dead code that reads as live. The architecture document correctly identifies this as the most common defect class. The `test/checks/filters.lua` and `test/checks/contracts.lua` checks are the right mitigation.

### 1.3 Module loading model

`bootstrap.lua` replaces ESO's missing `require` with a lookup that **raises on cache miss** rather than falling back to file I/O. `incha.txt` is both the manifest and the load order; every module self-registers before returning. This is the correct approach for the ESO environment. The alternative — silent `nil` on first use mid-fight — would be worse. The tradeoff is that circular requires and lazy loading are impossible, both of which are acceptable constraints.

### 1.4 Boss lifecycle

The wipe/leave distinction (A3) is handled correctly. `onWipe` is a soft reset; `onLeave` is a full teardown. `Trial` calls `cancelPending()` before `onWipe` so deferred callbacks from the ended pull cannot fire into the reset. `BossBase:after()` encapsulates `zo_callLater` with lifecycle tracking so forgetting to cancel is structurally harder. This is exactly the right approach.

### 1.5 State schema pattern

`BossBase.fromSchema` instantiates per-instance state from a class-level schema, with function values called to produce fresh objects. The `setmetatable` auto-link in `fromSchema` protects against the class of bug where a boss forgets `setmetatable(Boss, {__index = BossBase})`. Four classes had this bug; the engine now fixes it silently. Good engineering.

### 1.6 Dependency injection (A6)

`external-api/` gateways (`CombatAlerts`, `MechanicIcons`, `PositionIcons`) are injected once at `OnAddOnLoaded`. No boss file references `CombatAlerts` or `OSI` directly. The no-op defaults mean the addon degrades gracefully when dependencies are absent. Well-designed.

### 1.7 Known architectural debt

| Issue | Tracking | Severity |
|-------|----------|----------|
| Boss detection via English name literals (8/9 trials) | #123 | High |
| Compound boss files (ZmajaEncounter, OlmsEncounter) violate single-boss principle | A9, #129/#130 | Medium |
| All modules always resident — no lazy loading | A2 | Low (for current size) |
| Optional dependency binding happens once at `OnAddOnLoaded`; late publishers never seen | #112 | Medium |
| Translation strings drive boss detection logic | A8, #134 | Medium |

## 2. Code Review

### 2.1 Falgravn — shared `instant`/`started` table (design smell, masked bug)

**File:** [`trial/ka/boss/Falgravn.lua:844`](../trial/ka/boss/Falgravn.lua)

```lua
Falgravn.events = {
    beginCast = {
        instant = _beginCastEntry,   -- ← same table
        started = _beginCastEntry,   -- ← same table
    },
    ...
}
```

`_beginCastEntry` is assigned to **both** `instant` (fires on F+castTime=0) and `started` (fires on F+castTime>0). This means the same handlers fire for both instant-cast events and cast-started events on the same ability. For Njordal's `M_MOVE`, `M_BLOCK`, and Falgravn's `LIGHTNING` the dedup flags (`bMove`, `bBlock`, `bConnect`) prevent double-alerting, but only because the author anticipated this. For `INFUSER_CASTS`, `SACRIFICE`, `TORTURER_ESC`, `TORTURER_LA`, `BLOOD_FOUNT`, and `SHATTER_MID` there is no dedup guard — if any of those abilities has a non-zero cast time, the handler fires twice per event: once on F-started and once (via the interrupted timer → canceled by T) on F-instant, or vice versa.

The fix is to split the entries: instant-fire abilities (true instants) go in `instant`; abilities that emit a progress bar go in `started`. This is the contract the bucket names imply.

### 2.2 `Falgravn:onDied` doesn't call `BossBase:onDied`

**File:** [`trial/ka/boss/Falgravn.lua:502`](../trial/ka/boss/Falgravn.lua)

The boss overrides `onDied` but the override handles only `alertList`. The `prisonBars` table (keyed by `unitTag`, not `unitId`) is **never cleared on unit death**. If the unit whose prison bar is showing dies before `EFFECT_RESULT_FADED` fires, `prisonBars[unitTag]` retains a stale CA bar ID. The bar either already stopped itself (CA behaviour) or leaks until `onLeave`.

Additionally, `Falgravn:onDied` manually reimplements the two-key `alertList` cleanup that `BossBase:onDied` already does. The override should call `BossBase.onDied(self, ...)` and then handle `prisonBars` by iterating its unit tags.

### 2.3 Debug handler registered in production events

**File:** [`trial/ka/boss/Falgravn.lua:877`](../trial/ka/boss/Falgravn.lua)

```lua
gained = {
    ...
    [FALGRAVN_LINK_EFFECT]  = { type = AlertTypes.CUSTOM, fn = handleLinkEffect },
}
```

`handleLinkEffect` is labelled `-- DEBUG` and calls `Log.debug()` (no-op when debug is off), but the ability is still registered with `EventPipeline`, consuming a filter slot and going through the dispatch path on every gain event. This should be removed from the events table or conditionally included only when `Log.isEnabled()` at load time.

### 2.4 `Bahsei:onWipe` brittle manual reset

**File:** [`trial/rg/boss/Bahsei.lua:67`](../trial/rg/boss/Bahsei.lua)

The pattern of manually listing every `stateSchema` field in `onWipe` is repeated across most bosses and is fragile. Adding a field to `stateSchema` does not automatically add it to `onWipe`. The `state-reset.lua` check catches gaps at CI time but the onus is on the author to run the check. Four timers in Falgravn and three in Vrol are grandfathered as "countdown survives the wipe" — but without reading the grandfathered list, it is impossible to tell which omissions are intentional and which are bugs.

A safer pattern: `BossBase.fromSchema(self)` in `onWipe` for a defined reset-schema, separating pull-ephemeral state from pull-persistent state at the schema level.

### 2.5 `stateSchema` `= nil` trap — three unchecked fields

**Documented in:** [`docs/decisions/architecture.md`](../docs/decisions/architecture.md#A3) and `test/checks/state-reset.lua`

Lua drops nil keys from table constructors. A field with `= nil` in `stateSchema` is invisible to `BossBase.fromSchema`'s `pairs()` loop and therefore never initialized. Three fields in the tree have this problem (issue #113); the check cannot find them. These need a manual audit and `= false` / `= 0` replacements.

### 2.6 `Log.warn` always emits — potential chat noise

**File:** [`core/Trial.lua:193`](../core/Trial.lua)

`Log.warn` emits unconditionally regardless of the debug flag:

```lua
if not bossClass and Log.isEnabled() then
    ...
    Log.warn("%s: no boss matched. ...", ...)
```

Wait — this IS gated on `Log.isEnabled()`. Good. However in other call sites `Log.warn` is called without the gate. In `core/BossRegistry.lua` the normalize function falls back silently. The overall pattern is consistent; no action needed. *(Note: `Log.warn` calls outside a `Log.isEnabled()` guard should still be reviewed per-callsite for production noise.)*

### 2.7 `_pending` in EventDispatcher — module-level accumulation

**File:** [`core/EventDispatcher.lua:69`](../core/EventDispatcher.lua)

The interrupted-cast pending registry is module-level. Timers are cancelled correctly when T events arrive, and `capturedBoss`/`capturedContext`/`capturedAlerts` are closed over so stale callbacks cannot act on the wrong boss. However, if a network freeze or game hang prevents the T event and the cast duration timer fires, then immediately after the boss changes, the closure holds a reference to the old boss instance — which is the desired behavior. This is correct but the module-level table grows without bound in a theoretical long session with many started-but-never-completed casts. In practice with ~45-second fight durations this is negligible.

### 2.8 `RockgroveCommon.beginCastEntries` — shallow copy mutation risk

**File:** [`trial/rg/boss/Bahsei.lua:212`](../trial/rg/boss/Bahsei.lua)

```lua
local _beginCastEntry = {}
for k, v in pairs(RockgroveCommon.beginCastEntries) do _beginCastEntry[k] = v end
```

The entry *tables* themselves are shared by reference between `_beginCastEntry` and `RockgroveCommon.beginCastEntries`. Mutating an entry (e.g., `_beginCastEntry[EARTHQUAKE].fn = somethingElse`) would silently affect the source table and therefore all three RG bosses. Currently no boss mutates entries post-creation, so this is safe — but it is fragile. A comment acknowledging the shared-reference semantics would prevent a future maintainer from being surprised.

### 2.9 Test discovery is Unix-only

**Files:** [`test/checks/contracts.lua:75`](../test/checks/contracts.lua), [`test/checks/filters.lua:124`](../test/checks/filters.lua)

```lua
local p = io.popen('find trial -path "*/boss/*.lua" 2>/dev/null')
```

This is a POSIX `find` call. It will silently return an empty result on Windows without WSL, causing `contracts.lua` to report "no boss modules found" as a finding and `filters.lua` to skip the duplicate-key scan. The CI environment presumably runs Linux, so this doesn't block CI — but it prevents developers on Windows from running the suite locally.

### 2.10 Falgravn coordinate space — documented suspicion, still unverified

**File:** [`trial/ka/boss/Falgravn.lua:232`](../trial/ka/boss/Falgravn.lua)

The `UNVERIFIED COORDINATE SPACE` comment is thorough and the `checkNodeCoordSpace()` debug helper is well-designed. However, the comment has been there since the node tables were brought in from BSCHTKA and the coordinates have not been verified in-game. If the node origin is wrong, every Falgravn floor marker (`CONN_NODES`, `BLOOD_NODES`, `TORTURER_NODES`) is misplaced and the feature silently does nothing useful. This is a medium-priority correctness issue, not merely a code smell.

### 2.11 `Falgravn.events.beginCast.started` contains `handleBloodCleave` / `handleBloodFountain`

**File:** [`trial/ka/boss/Falgravn.lua:829`](../trial/ka/boss/Falgravn.lua)

These two handlers are in the shared `_beginCastEntry` table (same issue as 2.1) and call `CA.bar()` / `CA.ranged()` immediately on cast-start. The `started` bucket contract says "cast is in progress" — showing an alert here is correct. However, because the same table covers `instant`, if either ability is classified as instant by ESO (castTime=0), the alert fires via the `instant` path with no interrupt timer armed, which is also correct. The logic works but is harder to reason about than two separate tables.

## 3. Performance Review

### 3.1 Hot path: `onPowerUpdate`

Called multiple times per second. The path is:

1. `Throttle:shouldUpdate(healthPercent)` — O(1) floor+compare. ✅
2. `HealthRules.evaluate()` — linear scan, pre-compiled static text, no allocation on repeat calls. ✅
3. `AlertSink:showAction()` — one table lookup, calls handler if present. ✅

No allocations on the steady-state path. This is correct.

### 3.2 Hot path: `onUpdate` (200ms tick)

Falgravn's `onUpdate` calls `Lang.t()` 2–4 times per tick (once per `setRow` call). `Lang.t()` is a table lookup — O(1) — but the return value is immediately concatenated with `" " .. Lang.t("common_up")` or similar, allocating a new string every 200ms even when the displayed text hasn't changed. For a row that shows static text 90% of the time, this is 5 allocations/second of strings that will be immediately collected.

**Mitigation:** Cache the composed label strings in `stateSchema` or as module-level upvalues. The composed strings are static (label text doesn't change per-instance).

### 3.3 `GetGameTimeMilliseconds()` call density

`Timer:remaining()`, `Timer:isActive()`, and `Timer:isExpired()` each call `GetGameTimeMilliseconds()` independently. Falgravn's `onUpdate` has 4 active timers calling `:remaining()` — that is 4 C→Lua round-trips per 200ms tick. Bahsei's `onUpdate` correctly caches `now = GetGameTimeMilliseconds() / 1000` once and passes it to sub-functions. Falgravn should adopt the same pattern.

### 3.4 `EventPipeline.safe` wrapper overhead

The `safe()` wrapper uses `pcall()` on every event callback. In ESO, `pcall` has near-zero overhead unless an error is thrown, so this is acceptable. The alternative — letting an unhandled error in one boss crash the ESO event manager — is not worth the marginal cost. ✅

### 3.5 ESO event registration count

A boss with ~43 ability IDs registers 43 filtered handlers for `EVENT_COMBAT_EVENT` and some number for `EVENT_EFFECT_CHANGED`. ESO's per-event filter model means each registration is independent. This stays well within any practical limit and only the active boss's registrations are live at any time. ✅

### 3.6 `AlertSink` — no-allocation emit confirmed

The `emit` function comment confirms no payload allocation. The design comment "this runs on the boss-health hot path and every allocation there adds up" shows awareness of the constraints. ✅

### 3.7 `HealthRules.register` pre-compilation

Static texts are baked in at class load time via `rule._staticText`. On the hot path, `evaluate()` returns the pre-compiled string directly with no format call. This is the correct optimization for the most frequent code path. ✅

## 4. Strong Points

### 4.1 Per-ability event filtering is genuinely excellent

Most ESO addons register unfiltered `EVENT_COMBAT_EVENT` and discard events in Lua. Incha uses `REGISTER_FILTER_ABILITY_ID` correctly, pushing rejection to the C++ layer. This is the right engineering call and it is executed correctly across all 9 trials.

### 4.2 Load-time validation via `EventDispatcher.build()`

Type contracts (CAST_BAR forbidden in `instant`, DODGE/BLOCK/DEBUFF forbidden in `started`, CUSTOM requires `.fn`, TIMER_RESET requires `.timer` string) are asserted at addon load, not at first event. A misconfigured boss file causes a visible Lua error at login, not a silent no-op mid-fight. This is the correct approach.

### 4.3 BossBase lifecycle safety

The `after(ms, fn)` / `cancelPending()` / `cancelAfter(handle)` pattern is the right abstraction for the ESO timer API. Tracking handles on the instance and canceling all of them on wipe/exit eliminates an entire class of "deferred callback fires into a reset raid" bugs. `BossBase.fromSchema`'s auto-link to `BossBase` prevents another class of "cleanupAlertList is nil on wipe" bugs. Both fixes address bugs that had already shipped.

### 4.4 Domain-specific static check suite (10 checks)

The check suite is sophisticated:
- `contracts.lua`: factory loads, boss lifecycle contract, `alertList`→`onDied` pairing
- `filters.lua`: disjoint ability sets, declared sets exist, duplicate keys in source
- `state-reset.lua`: per-pull state must be reset on wipe
- `globals.lua`, `lang.lua`, `manifest.lua`, `load-order.lua`, `settings-usage.lua`, `syntax.lua`, `encoding.sh`, `branch-name.sh`

The "fail closed" principle — treating "no output" as a finding rather than clean — is the right call after `globals.lua` once reported clean on a broken toolchain.

### 4.5 AlertSink / Bridge decoupling

Boss code interacts with the UI exclusively through `AlertSink` methods (`showAction`, `setRow`, `clearRow`, `showHeader`, `clear`) and `Bridge` lifecycle hooks. No boss file imports `ui.Panel`. This makes swapping the renderer trivially possible and makes boss files testable without a UI.

### 4.6 Dependency injection for external APIs

`external-api/` gateways no-op silently when their dependency is absent. No boss file reads the `CombatAlerts` global directly. The O(1) lookup tables built at load time (`_cast`, `_ranged`, etc.) mean each CA call is a constant-time table lookup rather than a string switch.

### 4.7 Architecture decision log

`docs/decisions/architecture.md` is thorough, honest about tradeoffs, and links to tracking issues. The "Resolved questions" section prevents reopening settled questions. This is the kind of documentation that makes a codebase maintainable over years.

### 4.8 Log module design

`Log.debug()` gates on a runtime flag with an early return before the format call — no `string.format` work is done unless logging is enabled. `Log.warn()` always emits and is used for unexpected state that players need to see. This distinction is correct.

### 4.9 Lang module fallback

`Lang.t()` returns the key itself when no entry is found, not an empty string. Missing translations are visible on screen as their key name rather than silent blanks. The locale fallback to English with a one-time chat warning is pragmatic.

### 4.10 Test harness design

The ESO API stub (`test/harness/eso_api.lua`) with injectable mutable state (clock, zone, roles, ability durations) and log-replay testing with real encounter logs is a well-designed offline test strategy for an addon that cannot be unit-tested against the live game.

## 5. Weak Points

### 5.1 Boss detection is English-only for 8 of 9 trials

`BossRegistry:findByName()` compares against English name literals. The caveat is documented:

> *"Only KA currently declares Location bounds, which are locale-independent; every other trial relies solely on this path. See the 'Real Location bounds' item tracked as issue #123."*

For players on any non-English client (DE, FR, RU, ES, JP), 8 of 9 trials produce no alerts with no error — the addon silently does nothing. This is the highest-impact usability defect in the codebase.

### 5.2 Falgravn `instant`/`started` share the same table

Described in [§2.1](#21-falgravn--shared-instantstarted-table-design-smell-masked-bug). The dedup flags patch over the double-fire, but every new handler added to this table must independently implement dedup or silently fire twice. The architecture should not require that.

### 5.3 Compound boss files

`ZmajaEncounter.lua` (~637 lines per architecture docs) covers multiple entities as one class. `OlmsEncounter.lua` is similar. Both hand-partition the fixed 7 tracker rows between entities, so a conflict requires manual reshuffling. Health percent gates fire against whichever `bossN` slot last updated, which may be the wrong entity. The planned fix (A9: `Trial.activeBosses` list, keyed tracker rows) is the right direction but remains unimplemented.

### 5.4 Manual `onWipe` resets are brittle

Adding a field to `stateSchema` without adding it to `onWipe` silently leaks state across wipes. The `state-reset.lua` check catches this, but it requires knowing to run it and its grandfathered list is the only documentation of which omissions are intentional.

### 5.5 Test tooling is Unix-only on a Windows development environment

The developer's environment is Windows (`D:\dev\incha`). `io.popen('find trial ...')` does not work outside WSL. CI presumably passes because it runs on Linux, but the developer cannot run `contracts.lua` or `filters.lua` locally without WSL or a Cygwin-style `find`.

### 5.6 Falgravn floor marker coordinates are unverified

Documented in [§2.10](#210-falgravn-coordinate-space--documented-suspicion-still-unverified). The `CONN_NODES`, `BLOOD_NODES`, and `TORTURER_NODES` coordinates were inherited from BSCHTKA without re-measurement. If they're wrong, three position-icon features are silently non-functional.

### 5.7 Debug handler left in production events table

`FALGRAVN_LINK_EFFECT` is registered in the events table and goes through the full dispatch path on every `EFFECT_RESULT_GAINED` for that ability. See [§2.3](#23-debug-handler-registered-in-production-events).

### 5.8 `Falgravn:onDied` — prison bars not cleaned up on death

See [§2.2](#22-falgravnonDied-doesnt-call-bossbaseonDied). A unit's prison bar is tracked by `unitTag` (not `unitId`), so `onDied` (which receives `unitId`) cannot look it up. The bar either auto-stops or leaks until `onLeave`.

### 5.9 Translation strings drive boss detection (A8 violation)

23 boss detection fields use `nameAliases = { Lang.t("boss_zmaja") }` or similar, making a translation string decide whether an encounter activates. Translating the addon for a new locale silently changes detection behaviour.

### 5.10 Optional dependency binding is one-shot (issue #112)

If `CombatAlerts` or `OSI` publish their globals after `EVENT_ADD_ON_LOADED`, Incha never picks them up. The gateway captures `nil` and stays a no-op for the session with no diagnostic.

### P1 — Fix Falgravn `instant`/`started` shared table

**Files:** `trial/ka/boss/Falgravn.lua`  
**Risk:** Double-firing handlers on abilities without dedup guards. Silent wrong behaviour.

Split `_beginCastEntry` into two tables:

```lua
-- Abilities that fire instantly (castTime == 0 from ESO):
local _instantEntry = {
    [INFUSER_CASTS]         = { type = AlertTypes.CUSTOM, fn = handleInfuserCasts },
    [FALGRAVN_SACRIFICE]    = { type = AlertTypes.CUSTOM, fn = handleSacrifice },
    [FALGRAVN_TORTURER_ESC] = { type = AlertTypes.CUSTOM, fn = handleTorturerEsc },
    [FALGRAVN_TORTURER_LA]  = { type = AlertTypes.CUSTOM, fn = handleTorturerLa },
    -- Njordal instants:
    [FALGRAVN_M_MOVE]       = { type = AlertTypes.CUSTOM, fn = handleNjordalMoveBegin },
    [FALGRAVN_M_BLOCK]      = { type = AlertTypes.CUSTOM, fn = handleNjordalBlockBegin },
    [FALGRAVN_M_CLEAVE]     = { type = AlertTypes.CUSTOM, fn = handleBloodCleave },
    [FALGRAVN_BLOOD_FOUNT]  = { type = AlertTypes.CUSTOM, fn = handleBloodFountain },
}

-- Abilities that have a visible cast window (castTime > 0):
local _startedEntry = {
    [FALGRAVN_LIGHTNING]    = { type = AlertTypes.CUSTOM, fn = handleLightningBegin },
    [FALGRAVN_START_STAGE2] = { type = AlertTypes.CUSTOM, fn = handleStartStage2 },
    [FALGRAVN_SHATTER_MID]  = { type = AlertTypes.CUSTOM, fn = handleShatterMid },
    [FALGRAVN_OPEN_DOOR]    = { type = AlertTypes.CUSTOM, fn = handleOpenDoor },
}
```

The correct split requires one in-game session with `/incha debug` to verify which abilities have castTime > 0.

### P2 — Fix boss detection for non-English clients (#123)

**Files:** All `trial/*/boss/*.lua`, `trial/*/Factory.lua`  
**Risk:** Addon silently does nothing for 8/9 trials on any non-English client.

For each boss, measure the arena AABB by standing at the boundary and reading `/incha debug` coordinates, then declare `boss.location = Location.new(...)`. Remove `boss.name` / `boss.nameAliases` for bosses that have an AABB, or keep them as a secondary fallback.

Falgravn already has an AABB (though its node coordinates need verification — see P6). This work should start with trials that have simple arenas: Lokke (SS), Oaxiltso/Bahsei/Xalvakka (RG), Taleria (DSR).

### P3 — Fix `Falgravn:onDied` prison bar handling

**File:** `trial/ka/boss/Falgravn.lua:502`  
**Risk:** Prison bars leaking until zone exit when the debuffed player dies.

Replace the manual override with:

```lua
function Falgravn:onDied(context, alerts,
                          unitTag, sourceUnitTag, sourceUnitId, unitId,
                          sourceUnitName, unitName)
    -- Base handles alertList by unitId:
    BossBase.onDied(self, context, alerts,
        unitTag, sourceUnitTag, sourceUnitId, unitId, sourceUnitName, unitName)
    -- Prison bars are keyed by unitTag — look it up here if needed.
    -- Note: EFFECT_RESULT_FADED normally fires on death and clears prisonBars;
    -- this is a fallback for cases where it doesn't.
    if unitTag and self.prisonBars[unitTag] then
        CA.castAlertsStop(self.prisonBars[unitTag])
        self.prisonBars[unitTag] = nil
    end
end
```
